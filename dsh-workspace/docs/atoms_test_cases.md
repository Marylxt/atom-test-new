# Atoms AI 应用生成平台测试用例设计

> 依据：`docs/atoms_spec.txt`
> 被测系统：Atoms 应用生成平台（自然语言需求 → 产品经理 Agent → 架构师 Agent → 工程师 Agent → 可运行 Web 应用）
> 需求映射：三个 Agent 接力生成 → 链路契约（CHN，见 §5）；必须可交互 → 生成质量（QUAL，见 §6）；数据持久化 → 持久化（DATA，见 §7）；支持多轮修改 → 迭代（ITER，见 §8）；支持版本回滚 → 版本（VER，见 §9）；响应时间 ≤ 30 s → 端到端（E2E，见 §10）

---

## 1. 测试范围与分层策略

| 层 | 被测对象 | 核心问题 | 用例前缀 |
|---|---|---|---|
| 链路层 Chain | 需求解析 → PM 输出 → 架构输出 → 工程输出 → 构建部署 | 交接是否契约化、需求是否透传、失败是否可定位可恢复 | `CHN` |
| 生成质量 Quality | 生成产物的功能、交互、结构、可用性 | 是否真"可运行、可交互"，而不是看起来完整 | `QUAL` |
| 持久化 Data | 数据模型、存储写入、刷新/重启后的数据存活、隔离 | 数据是写进存储，还是只活在前端内存里 | `DATA` |
| 多轮修改 Iteration | 增量修改、约束保持、上下文传递 | 改一处是否破坏另一处，历史约束是否被遗忘 | `ITER` |
| 版本回滚 Version | 版本快照、回滚、回滚后可用性与隔离 | 回滚是否真回到旧状态且仍可运行 | `VER` |
| 端到端 E2E | 全链路 + 并发 + 30 s 时延 + 稳定性 | 是否满足 30 s 与并发可用性 | `E2E` |

**分层原则**：链路层契约不成立时，上层结论不可信（例如 PM 漏掉"数据要保存"这条需求，QUAL/DATA 用例必然失败但根因在 CHN）。因此**执行顺序为 CHN → QUAL → DATA → ITER → VER → E2E**；ITER/VER 必须以 QUAL 与 DATA 通过的版本为前置基线，否则"修改后仍可用""回滚后仍可用"的判定无意义。

**核心测试思路（本设计的判定基石）**：

1. **原子需求单元（Atomic Requirements, AR）**：把一条自然语言需求逐句拆成**带唯一编号、可客观判定**的最小单元（含显式要求与隐含推导），全流程追踪它的存活情况。
   - 示例需求："做一个记账应用，能添加支出、能按分类看统计，数据要保存下来"。拆解：
     - **AR-1**：可添加一条支出记录（含金额、分类、日期）。
     - **AR-2**：可按分类查看统计。
     - **AR-3**（推导）：删除/编辑记录。
     - **AR-4**（推导）：数据在刷新/重启后仍存在。
     - **AR-5**（推导）：无数据时有空状态提示。
   - 每个 AR 在 4 个产物中逐项勾选：**PM 需求文档 / 架构数据模型与接口 / 生成代码 / 运行时实际行为**。任意一环缺失即为缺陷，且能精确定位到 Agent。
2. **交接契约（Handoff Contract）**：每份 Agent 产物必须可结构化校验（JSON Schema），字段缺失即链路缺陷（详见 §2.2）。
3. **可运行性自动判定**：不依赖人工"看着像能跑"，而是用浏览器自动化 + 控制台/网络错误采集做客观断言（详见 §2.3）。
4. **持久化差异法**：同一操作在"会话内 / 刷新后 / 服务重启后"三次读取同一数据，用差异判定是否真正落盘（详见 §2.4）。

## 2. 测试环境、基准需求与判定基础设施

### 2.1 环境与固定条件

| 项 | 配置 |
|---|---|
| 平台版本 | 前后端与三个 Agent 的提示词/模型版本全部记录（含模型名、版本、温度、max_tokens） |
| 部署 | 单实例基准（E2E 压测口径）；平台服务与"生成的应用"运行环境**分别可观测** |
| 生成产物运行环境 | 独立沙箱容器/预览域名，可重启（用于 DATA 的持久化验证），可快照（用于 VER） |
| Agent 可观测 | 全链路 trace_id；分别采集 PM 耗时 / 架构耗时 / 工程耗时 / 构建部署耗时 / 总耗时；每次交接的输入输出原文留档 |
| 浏览器自动化 | 具备 DOM 操作、断言、控制台日志与 network 采集能力（如 Playwright） |
| 数据观测 | 生成应用的存储后端可直连读取（DB/对象存储/KV），用于"API 能读到"与"UI 能看到"的双重验证 |
| 冻结项 | 测试期间固定：模型版本、提示词版本、Agent 编排配置；任一变更须重新基线化全部用例 |

### 2.2 交接契约（CHN 用例的判定标准，须先定义后测试）

| 交接点 | 产物 | 必填字段（示例基线，实际以平台 schema 为准） |
|---|---|---|
| 用户 → PM | 需求文档 | 功能点列表（每条可验收）、角色、页面/流程清单、数据实体与字段、非功能要求（含"需持久化"标记） |
| PM → 架构师 | 架构方案 | 页面/路由清单、数据模型（实体+字段+类型+关系）、接口清单（方法+路径+请求/响应）、存储选型、**需求→设计追溯表（AR 全覆盖）** |
| 架构师 → 工程师 | 实现产物 | 文件清单、代码、依赖清单、数据访问层实现、构建/启动脚本 |
| 工程师 → 平台 | 部署产物 | 可访问 URL、构建日志、启动健康检查结果、版本号 |
| 每次交接 | 元数据 | trace_id、父任务 id、schema 版本、耗时、状态（成功/失败/重试次数） |

**硬性规则**：任一交接物缺必填字段，或架构方案的需求追溯表未覆盖全部 AR，**判定为链路缺陷（P0）**，无论最终应用是否"看起来能跑"。

### 2.3 可运行性与可交互性判定标准（QUAL 用例的判定标准）

| 判定项 | 客观判定方式 | 通过标准 |
|---|---|---|
| 可运行 | 访问生成应用 URL，页面 HTTP 状态码、首屏渲染完成、无未捕获 JS 异常 | 200 + 首屏渲染成功 + 控制台 error 数 = 0 |
| 可交互（非静态图） | 遍历 DOM，统计可交互元素（`button`、`input`、`select`、`[role=button]`、带 onclick 的节点）与已绑定事件处理器数量 | ≥ 1 个真实交互元素；无 `pointer-events:none` 空壳按钮；无"点了没反应"（点击后 DOM 或网络请求发生变化） |
| 核心流程可用 | 按需求生成的**需求验收问题集（Acceptance Questions, AQ）**逐条执行（详见 §2.5） | AQ 通过率 ≥ 90%，且每条需求的 P0 流程 100% 通过 |
| 请求非伪造 | 交互过程中采集 XHR/fetch；若需求涉及数据读写，必须有真实网络请求或本地存储写入 | 数据类需求必须出现真实持久化调用，禁止纯前端写死数据冒充 |
| 无占位/桩代码 | 扫描产物与 UI 文本 | 不出现 `TODO`、`Lorem ipsum`、`示例数据`、`coming soon`、`功能开发中` 等未实现标记（空状态提示文案除外） |

### 2.4 持久化判定标准（DATA 用例的判定标准）

对每一次"写"操作，按顺序做三档观测，**三档全部一致才算持久化通过**：

1. **S1 会话内**：同页面/同会话内重新读取（刷新列表、重进页面），数据存在。
2. **S2 刷新后**：整页刷新（清空前端内存状态）+ 新开无痕窗口访问，数据仍存在。
3. **S3 服务重启后**：重启生成应用的运行容器，再访问，数据仍存在；同时直连存储后端确认记录存在且字段完整。
4. **反例排除**：禁止用 `localStorage` 单点冒充"服务端持久化"（若需求要求多端/多人可见），须按需求判定存储层级别。

### 2.5 需求验收问题集（AQ，所有 QUAL/DATA/ITER/VER 用例共用）

| 数据集 | 构成 | 用途 |
|---|---|---|
| `REQ-A` 标准需求集 | ≥ 20 条覆盖典型类型（记账、待办、图书管理、问卷、CRM 简版、表单收集） | 主基线，每条拆出 AR |
| `REQ-B` 模糊/口语化需求集 | ≥ 10 条，含省略主语、情绪化描述（"帮我搞个好看又简单的排班表"） | 澄清能力、合理默认值 |
| `REQ-C` 高复杂度需求集 | ≥ 5 条，含 ≥ 5 个实体、多角色权限、复杂统计 | 链路容量、需求透传率压力 |
| `REQ-D` 冲突/边界需求集 | ≥ 5 条，含自相矛盾、超平台能力（如"要能接微信支付"） | 冲突识别、能力边界声明 |
| `AQ` 验收问题集 | 对应每条 AR 的 1~3 条可判定问题（如"添加一条 100 元餐饮支出后，统计页餐饮合计是否 +100？"） | 生成质量的客观判定，禁止人工主观"看起来不错" |

### 2.6 判定方式

- **客观项**（HTTP 状态、控制台错误数、DOM 元素数、网络请求存在性、存储记录存在性、时延、版本号）：脚本自动断言。
- **语义项**（需求透传率、澄清合理性、可交互性人工复核、UI 可用性）：**两名评测员独立标注 + 第三人仲裁**；抽样 ≥ 30 条时用一致性（Cohen's κ ≥ 0.8），否则结论不可信。
- 所有比率型指标须记录：样本量、分子、分母、Wilson 95% 置信区间。

## 3. 指标定义与阈值（验收基线）

### 3.1 链路层

| 指标 | 定义 | 阈值 |
|---|---|---|
| 链路成功率 | 三个 Agent 全部成功并产出可访问 URL 的需求数 / 需求总数 | ≥ 0.95 |
| 需求透传率 | 在最终运行时行为中成立的 AR 数 / AR 总数 | ≥ 0.90，且**核心 AR（P0）无丢失** |
| 交接契约合规率 | 交接物通过 schema 校验且追溯表覆盖全部 AR 的次数 / 总交接次数 | 100% |
| 链路可定位性 | 失败任务能准确指出失败 Agent 与失败环节的比例 | 100% |
| 失败恢复 | 单 Agent 失败后按重试/续跑恢复且不重跑已完成环节的比例 | ≥ 0.90 |
| 链路重现性 | 同一需求 + 同一提示词版本，AR 集合一致率 | ≥ 0.80（允许实现细节差异，不允许需求增减） |

### 3.2 生成质量

| 指标 | 定义 | 阈值 |
|---|---|---|
| 可运行率 | 部署成功且首屏无致命错误的应用数 / 总数 | ≥ 0.95 |
| 可交互率 | 通过 §2.3 交互判定（存在真实交互且点击有响应）的应用数 / 总数 | 100% |
| AQ 通过率 | 通过的验收问题数 / AQ 总数 | ≥ 0.90；需求级 P0 流程 = 100% |
| 占位代码率 | 含未实现占位标记的项目数 / 总数 | 0（可运行相关，P0） |
| 结构合理性 | 路由/页面/实体与架构方案一致的比例 | ≥ 0.95 |
| 需求透传率 | 同 §3.1 | ≥ 0.90 |
| 响应完整性 | 无空白页、无白屏、无只有标题的页面 | 100% |

### 3.3 持久化

| 指标 | 定义 | 阈值 |
|---|---|---|
| 持久化通过率 | 通过 S1+S2+S3 三档观测的写操作数 / 写操作总数 | ≥ 0.98 |
| 数据完整性 | 写入后读取的字段完整、类型正确、无丢字段/截断 | 100% |
| 数据隔离 | 不同用户/不同应用之间的数据不串号 | 100%（P0） |
| 并发写一致性 | 并发写入下无数据丢失、无重复主键、无覆盖写 | 丢失率 = 0 |
| 更新与删除持久化 | 编辑、删除同样通过三档观测 | 100% |

### 3.4 多轮修改

| 指标 | 定义 | 阈值 |
|---|---|---|
| 修改生效率 | 修改后目标 AR 在运行时成立的比例 | ≥ 0.95 |
| 既有功能回归率 | 修改未破坏的既有 AR 数 / 既有 AR 总数 | ≥ 0.95（**不得破坏 P0 流程**） |
| 历史约束保持率 | 历史轮次的约束（如"数据要保存""用中文""要能导出"）在新版本中仍成立的比例 | ≥ 0.95 |
| 数据延续性 | 修改前已存在的数据在修改后仍存在且可见 | 100%（**修改不得清空数据**，P0） |
| 多轮衰减 | 第 N 轮（N ≥ 5）与第 1 轮的修改生效率差值 | ≤ 10 个百分点 |
| 修改轮次可追溯 | 每轮修改可定位到对应的需求增量与代码变更 | 100% |

### 3.5 版本回滚

| 指标 | 定义 | 阈值 |
|---|---|---|
| 回滚成功率 | 回滚后应用可访问且可运行的比例 | 100% |
| 回滚一致性 | 回滚后运行时行为与目标历史版本一致的比例（按该版本 AQ 判定） | ≥ 0.98 |
| 回滚完整性 | 代码、数据模型、配置、依赖整体回到该版本，无"半新半旧"混杂 | 100% |
| 回滚后数据策略一致性 | 数据按已明确声明的策略处理（保留 / 迁移 / 备份），且无静默丢失 | 100% |
| 版本可追溯 | 每个版本可查看版本号、时间、需求描述、变更差异 | 100% |
| 回滚可逆 | 从回滚后的版本再前进到最新版本，功能与数据符合预期 | ≥ 0.95 |

### 3.6 端到端

| 指标 | 定义 | 阈值 |
|---|---|---|
| 生成响应时间 | 从用户提交需求到**应用可访问且首屏可交互** | P95 ≤ 30 s |
| 分段耗时 | PM / 架构 / 工程 / 构建部署各自耗时 | 全部记录，超阈样本可归因 |
| 修改响应时间 | 单轮修改提交到新版本可访问 | P95 ≤ 30 s |
| 回滚响应时间 | 回滚指令发出到目标版本可访问 | P95 ≤ 30 s |
| 并发能力 | 20 并发生成、持续 15 min | 成功率 ≥ 95%，P95 ≤ 30 s（若为共享模型配额，须记录配额与队列行为） |

> 注：`30 秒` 在需求中未限定口径，本设计取**端到端首次可交互**为验收口径，并同时记录各 Agent 分段耗时、首个可见进度反馈时间（TTFB 类）、修改与回滚耗时作为观测项。若产品定义为首 token/首屏骨架口径，需回改 §3.6 阈值并同步 E2E-01/02。**该口径为发布前必须澄清项，见 §11。**

每条用例统一按以下结构执行与留档：**前置条件 → 操作步骤 → 预期结果 → 实际结果/结论**。所有用例须记录：trace_id、平台版本、模型/提示词版本、生成应用 URL、版本号、样本量。

## 5. 多智能体链路用例（CHN）

### CHN-01 标准需求的三 Agent 接力端到端成功
- **优先级**：P0
- **前置条件**：`REQ-A`（≥ 20 条）就绪并已拆解出 AR 清单；平台与三个 Agent 健康；提示词版本冻结；浏览器自动化与存储观测就绪。
- **操作步骤**：
  1. 逐条提交需求，记录 trace_id 与提交时间。
  2. 采集三段产物：PM 需求文档、架构方案、工程产物与部署 URL；校验每份产物是否符合 §2.2 交接契约 schema。
  3. 核对架构方案的**需求追溯表**是否覆盖全部 AR（含推导 AR）。
  4. 访问生成应用，执行该需求的 AQ，逐条判定。
  5. 统计链路成功率与需求透传率，并对每条丢失的 AR 定位到具体 Agent 环节。
- **预期结果**：链路成功率 ≥ 0.95；交接契约合规率 100%；需求透传率 ≥ 0.90 且核心 AR 无丢失；所有部署产物返回可访问 URL（HTTP 200）；失败样本须给出失败 Agent 与失败原因（可定位率 100%）。
- **实际结果 / 结论**：＿＿

### CHN-02 交接契约完整性与需求透传（断链定位）
- **优先级**：P0
- **前置条件**：可对单个 Agent 产物做 schema 校验；准备包含**易被忽略的隐性需求**的需求集（如"操作要能撤销""金额要能改""手机上看也正常"）。
- **操作步骤**：
  1. 对 `REQ-A`+`REQ-C` 全量执行，保存三份交接物原文。
  2. 逐条比对：PM 的功能点是否全部进入架构的数据模型/接口 → 架构的实体与接口是否全部在代码中实现 → 代码实现是否在运行时生效。
  3. 对每个断点记录：缺失字段、缺失环节（PM/架构/工程/构建）、是否导致 AQ 失败。
  4. 故意构造 1 条 PM 产物缺失"持久化标记"的 mock 交接，验证平台是否拦截。
- **预期结果**：所有交接物通过 schema 校验；需求追溯表 AR 覆盖率 100%；mock 缺失字段的交接**必须被平台拦截并报错**，不得静默继续；存在断链时能精确输出"哪条 AR 在哪一环丢失"。
- **实际结果 / 结论**：＿＿

### CHN-03 需求歧义时的澄清与合理默认值
- **优先级**：P1
- **前置条件**：`REQ-B`（模糊/口语化，≥ 10 条）就绪；已记录平台是否具备反问机制。
- **操作步骤**：
  1. 提交模糊需求，记录平台行为：反问澄清 / 直接生成。
  2. 若直接生成，检查是否明确声明了所做的默认假设（如"默认币种为人民币""默认单用户"）。
  3. 按平台声明的假设执行 AQ，判定实现与假设是否一致。
  4. 对同一条模糊需求提交两次，比较默认假设的稳定性。
- **预期结果**：不出现"按错误理解直接生成且不声明假设"；声明的假设与实现一致率 100%；同一需求两次生成的默认假设一致率 ≥ 0.80；澄清提问（若有）需 ≤ 2 轮，且不阻塞在无人应答状态。
- **实际结果 / 结论**：＿＿

### CHN-04 单 Agent 失败与恢复（可重试、可续跑）
- **优先级**：P0
- **前置条件**：可分别注入 PM / 架构 / 工程 Agent 的超时、5xx、schema 不合规输出（mock 或故障开关）。

  4. 检查已完成环节是否被重跑（对比 trace 中的 Agent 调用次数与产物哈希）。

## 7. 数据持久化用例（DATA）

### DATA-01 基础写入的持久化三档观测
- **优先级**：P0
- **前置条件**：应用已部署；存储后端可直连读取；可重启应用容器。
- **操作步骤**：
  1. 执行一条写操作（新增记录），记录写入内容与时间。
  2. **S1**：在同一会话内重新读取（刷新列表 / 重进页面），核对数据。
  3. **S2**：整页刷新 + 新开无痕窗口访问，核对数据。
  4. **S3**：重启应用容器后访问，核对数据；并直连存储确认记录存在、字段完整。
- **预期结果**：S1/S2/S3 三档数据均存在且一致；存储后端确有对应记录；字段无丢失、类型正确；持久化通过率 ≥ 0.98。
- **实际结果 / 结论**：＿＿

> **说明**：若 S1 通过而 S2/S3 失败，说明数据仅存于前端内存或 `localStorage` 且未落服务端；若 S3 失败而 S2 通过，说明存储为容器内临时文件（非持久卷）。两者均判 P0 缺陷，且须在报告中指出具体存储层问题。

### DATA-02 更新与删除的持久化

- **预期结果**：编辑与删除同样通过三档观测（100%）；统计结果随增删改实时正确；存储层删除真实生效；无"UI 删了但存储还在""UI 改了但统计没变"。
- **实际结果 / 结论**：＿＿

### DATA-03 数据完整性、类型与边界值

- **操作步骤**：

  2. 等待新版本生成完成，记录新版本号、耗时、修改前后的代码/接口差异。
  3. 执行新需求的 AQ，确认修改生效。
  4. **重跑首轮 AQ 全集**，确认无回归。
  5. 核对历史约束清单（如"数据要保存"）是否仍成立。
- **预期结果**：修改生效率 ≥ 0.95；既有功能回归率 ≥ 0.95 且 P0 流程 100% 不破坏；历史约束保持率 ≥ 0.95；新版本产生且旧版本仍保留可访问；修改不产生占位代码。
- **实际结果 / 结论**：＿＿

### ITER-02 跨轮上下文与历史约束保持（多轮累积）
- **优先级**：P0
- **前置条件**：同 ITER-01；准备 ≥ 5 轮递进修改脚本，其中**第 1 轮含隐性约束**（如"所有界面用中文""日期显示为 YYYY-MM-DD"），后续轮次不再重复提及。
- **操作步骤**：
  1. 连续执行 5 轮修改（每轮一个独立需求点）。
  2. 每轮结束后立即核验：① 本轮修改生效；② 前 N-1 轮所有功能仍可用；③ 第 1 轮的隐性约束仍生效。
  3. 记录约束失效首次出现的轮次。
  4. 对比第 5 轮与第 1 轮的修改生效率。
- **预期结果**：历史约束保持率 ≥ 0.95；多轮衰减 ≤ 10 个百分点；不出现"越改越忘"（如第 3 轮后界面变英文、日期格式漂移）；每轮修改均可追溯到对应需求增量。
- **实际结果 / 结论**：＿＿

### ITER-03 修改对既有数据的影响（数据延续性）
- **优先级**：P0
- **前置条件**：首轮已写入 ≥ 5 条真实数据（记录 ID 与内容快照）；修改需求涉及数据结构变更（如"分类改为可自定义，替换原固定分类"）。
- **操作步骤**：
  1. 记录修改前的数据快照（条数、ID、字段值、统计结果）。
  2. 提交**会改变数据结构**的修改，等待新版本。
  3. 检查：数据条数是否保留、旧分类数据如何迁移（映射 / 置空 / 保留）、统计是否正确。
  4. 按 DATA-01 三档观测重新验证持久化。
  5. 检查是否声明了不兼容变更（如必须重置数据）。
- **预期结果**：数据延续性 100%（不得静默清空）；结构变更须有明确迁移策略并生效；旧数据在新结构下可正常展示与统计；若必须破坏性变更，须**显式提示并获得确认**，不得静默丢数据；变更后持久化仍通过三档观测。
- **实际结果 / 结论**：＿＿

### ITER-04 冲突修改与需求反转
- **优先级**：P1
- **前置条件**：已有首轮版本；准备相互冲突的修改序列。
- **操作步骤**：

  3. 第 3 轮：要求删除某功能（如删除备注字段），检查是否残留字段、接口、UI 入口。

- **预期结果**：后一轮要求完全覆盖前一轮（无残留逻辑/字段/入口）；反转修改后功能自洽；删除类修改彻底（代码、UI、数据模型、接口同步），不产生悬挂引用报错。

### ITER-05 并发/连续修改的版本与数据一致性
- **优先级**：P1
- **前置条件**：可并发提交修改请求；具备版本列表查询能力。

- **预期结果**：并发修改有明确策略（排队或冲突提示），不出现静默丢失某一方的修改；版本号单调且唯一、无缺口歧义；最终版本内部自洽；并发期间数据不损坏。

### ITER-06 修改失败的回滚与脏版本防护
- **优先级**：P0
- **前置条件**：可注入修改阶段的故障（工程 Agent 失败、构建失败、部署失败）。
- **操作步骤**：
  1. 提交修改，注入构建失败。
  2. 检查当前可访问版本：是否仍为**上一成功版本**且功能正常。
  3. 检查是否产生"半成品版本"（列表可见但不可访问、访问报错）。
  4. 修复后重试同一修改，确认最终生效且数据未损。
- **预期结果**：修改失败时线上仍稳定停留在上一成功版本（可用性不被破坏）；不产生可访问的脏版本；失败版本有明确失败标记且不可被误"回滚"为正式版；重试成功后功能与数据均正常。

- **预期结果**：单点修改的变更范围收敛（仅影响相关文件/组件，无全量重写迹象）；不引入与修改无关的视觉/交互变更；未提及的功能保持原样（差异可比对证明）；修改耗时不因全量重写显著劣化。
- **实际结果 / 结论**：＿＿

## 9. 版本回滚用例（VER）

> 通用约束：回滚相关的三个语义必须**在测试前明确**，否则用例无法判定：① 版本粒度（每次修改产生一个版本，还是用户手动保存快照）；② 回滚是否产生新版本（推荐产生新版本以保持历史线性）；③ **回滚后数据如何处理**（保留当前数据 / 一并回退到该版本时的数据快照 / 迁移到旧结构 / 提供备份）。本设计对 ③ 采用**双分支验证**：平台须明示策略，且实际行为与该策略一致。

### VER-01 回滚到历史版本的功能一致性
- **优先级**：P0
- **前置条件**：同一应用存在 ≥ 3 个版本（V1/V2/V3），每个版本均有 AQ 记录与截图；当前为 V3。
- **操作步骤**：
  1. 查看版本列表，确认版本号、时间、需求描述、变更差异可见。
  2. 执行回滚到 V1，记录耗时与结果。
  3. 访问线上应用，按 **V1 的 AQ 全集**执行判定。
  4. 与 V1 的存档截图/DOM 快照比对结构一致性。
  5. 记录回滚响应时间。
- **预期结果**：回滚成功率 100%；回滚后行为与 V1 一致率 ≥ 0.98（V1 的 AQ 全部通过，且不含 V2/V3 引入的功能）；结构一致性 ≥ 0.95；回滚响应时间 P95 ≤ 30 s；回滚操作有明确结果提示。
- **实际结果 / 结论**：＿＿

### VER-02 回滚的完整性与半新半旧防护
- **优先级**：P0
- **前置条件**：V1 → V2 之间发生过**跨层变更**：数据模型加字段、新增接口、新增依赖、改配置（如分页大小）。
- **操作步骤**：
  1. 回滚到 V1。
  2. 逐层核对：代码、数据模型（字段是否回退）、接口清单（V2 新增接口是否移除或明确保留）、依赖清单、配置项。
  3. 检查是否残留 V2 的 UI 入口但后端已回退（或反之），并尝试触发。
  4. 检查版本号与变更记录是否与回滚动作一致。
- **预期结果**：回滚完整性 100%（四层一致回到 V1）；无"UI 是 V1 但接口是 V2"的混杂；无悬挂引用导致的运行时报错；回滚动作在版本历史中显式记录（含操作人、时间、源版本、目标版本）。
- **实际结果 / 结论**：＿＿

### VER-03 回滚后的数据策略（双分支）
- **优先级**：P0
- **前置条件**：V1 时存在数据 D1（≥ 3 条）；V2 引入新字段并写入数据 D2；平台**已明示**回滚数据策略（分支 A：保留数据并按旧结构兼容读取；分支 B：数据一并回退到 V1 快照并保留备份）。
- **操作步骤**：
  1. 回滚到 V1，记录策略声明内容。
  2. 分支 A：访问应用，检查 D1 与 D2 是否可见、新字段数据如何呈现（忽略 / 降级显示），是否报错。
  3. 分支 B：检查 D1 是否恢复、D2 是否有备份可下载/恢复，且回滚前数据未静默丢失。
  4. 按 DATA-01 三档观测验证回滚后持久化仍正常（回滚后可继续写入并存活）。
  5. 再前进到 V3，检查数据是否可重新访问（可逆性）。
- **预期结果**：实际数据行为与平台声明策略一致率 100%；**不出现静默数据丢失**（P0）；回滚后应用可正常读写并持久化；新旧结构不兼容时给出明确提示而非报错崩溃；前进回滚可逆率 ≥ 0.95。
- **实际结果 / 结论**：＿＿

### VER-04 回滚后继续修改（分支演进）
- **优先级**：P0
- **前置条件**：存在 V1/V2/V3；当前已回滚到 V1。
- **操作步骤**：
  1. 在回滚后的 V1 基础上提交一个新修改（与 V2/V3 内容不同）。
  2. 检查新版本号分配方式（覆盖 V2 破坏历史 / 新增 V4 保留历史）。
  3. 检查是否可再回滚到 V2/V3，且回滚后行为正确。
  4. 对 V4 执行 AQ 与新需求 AQ。
- **预期结果**：回滚后可继续正常修改并生成新版本；**历史版本不被覆盖删除**（可再回到 V2/V3）；版本关系清晰（线性或分支，须有明确表示）；新版本功能与数据均正常。
- **实际结果 / 结论**：＿＿

### VER-05 连续多次回滚与版本遍历
- **优先级**：P1
- **前置条件**：存在 ≥ 5 个版本（V1~V5），每版 AQ 已存档。
- **操作步骤**：
  1. 依次执行 V5 → V3 → V1 → V4 → V5 的回滚/前进操作（覆盖跳版本回滚与往返）。
  2. 每次操作后按目标版本 AQ 抽检（每版 ≥ 3 条 P0 流程）。
  3. 检查系统状态是否漂移（如同一版本的两次访问行为不一致）。
  4. 记录每次耗时与失败次数。
- **预期结果**：每次回滚成功且与目标版本一致；同一版本多次访问行为一致（无状态累积漂移）；往返操作不产生数据损坏或版本丢失；连续操作失败率 = 0；耗时无随操作次数增长而显著劣化。
- **实际结果 / 结论**：＿＿

### VER-06 回滚过程中的数据写入（竞态）
- **优先级**：P1
- **前置条件**：可并发触发"用户写数据"与"回滚操作"。
- **操作步骤**：
  1. 在用户侧持续写入数据（每 2 s 一条）。
  2. 同时触发回滚到旧版本。
  3. 记录回滚期间写入的请求结果（成功/失败/超时）与存储最终状态。
  4. 检查是否出现部分写入、结构不匹配的脏数据、应用报错。
- **预期结果**：回滚期间有明确的写入策略（拒绝并提示"版本切换中"或排队），不产生结构不匹配的脏数据；无数据损坏导致后续页面报错；回滚完成后系统可正常读写；期间错误提示可读、不含内部堆栈。
- **实际结果 / 结论**：＿＿

### VER-07 回滚权限与操作可追溯（含误操作防护）
- **优先级**：P1
- **前置条件**：准备两种角色账号（应用所有者 / 无权限协作者）；存在 ≥ 2 个版本。
- **操作步骤**：
  1. 无权限用户尝试回滚，观察是否被拒绝。
  2. 所有者执行回滚，检查版本历史是否记录操作人、时间、源/目标版本。
  3. 检查回滚前是否有确认提示（尤其当目标版本会导致数据策略变化时）。
  4. 对已删除的版本（若有删除功能）尝试回滚，检查错误处理。
- **预期结果**：越权回滚被拒绝（403）且无副作用；回滚操作 100% 可追溯（操作人/时间/源版本/目标版本）；破坏性回滚（会丢数据）必须二次确认；对不存在/已删除版本回滚返回明确错误而非 5xx。
- **实际结果 / 结论**：＿＿

### VER-08 回滚与生成质量的下限保障
- **优先级**：P1
- **前置条件**：目标历史版本本身质量合格（已通过 QUAL-03），准备回滚到该版本。
- **操作步骤**：
  1. 回滚到历史版本。
  2. 对该版本执行 §2.3 全部可运行性与可交互性判定，而非仅核对"页面能打开"。
  3. 检查依赖与构建是否使用版本当时的锁定清单（可复现构建）。
- **预期结果**：回滚后仍满足可运行率与可交互率要求（控制台 error = 0、交互有效）；构建可复现（依赖版本锁定，不因时间推移拉到新版本导致失败）；不出现"回滚成功但应用跑不起来"。
- **实际结果 / 结论**：＿＿

## 10. 端到端用例（E2E）

### E2E-01 生成响应时间基线（含分段耗时）
- **优先级**：P0
- **前置条件**：单实例部署；`REQ-A` 冻结；冷启动完成（预热 ≥ 10 次生成）；缓存开关状态固定并记录。
- **操作步骤**：
  1. 按 `REQ-A` 抽样 ≥ 30 条，串行提交（避免相互排队干扰），记录：提交 → 首个进度反馈 → PM 完成 → 架构完成 → 工程完成 → 构建部署完成 → 首屏可交互。
  2. 计算总耗时与各分段耗时 P50/P90/P95/P99。
  3. 对超 30 s 的样本逐条归因（PM 慢 / 架构慢 / 工程慢 / 构建排队 / 部署慢）。
- **预期结果**：端到端 P95 ≤ 30 s；P50 ≤ 20 s；无样本超时未返回结果；分段耗时 100% 可采集；超阈样本须有归因记录且超阈比例 ≤ 5%。
- **实际结果 / 结论**：＿＿

### E2E-02 修改与回滚的响应时间
- **优先级**：P0
- **前置条件**：存在一个已生成的基座应用；可重复提交修改与回滚。
- **操作步骤**：
  1. 串行提交 ≥ 20 次单点修改，记录每次提交到新版本可访问的耗时。
  2. 串行执行 ≥ 20 次回滚，记录耗时。
  3. 分别计算 P50/P95/P99，并与首次生成耗时对比。
  4. 对超阈样本归因。
- **预期结果**：修改 P95 ≤ 30 s；回滚 P95 ≤ 30 s；修改耗时显著低于首次生成（应复用已有产物，不得每次全量重建）；无操作长时间无反馈；超阈样本有归因。
- **实际结果 / 结论**：＿＿

### E2E-03 并发生成负载
- **优先级**：P1
- **前置条件**：压测工具就绪；20 并发 = 20 个持续虚拟用户；时长 15 min；记录模型配额与队列上限；缓存状态固定。
- **操作步骤**：
  1. 以 20 并发混合提交 `REQ-A`(80%) 与 `REQ-B`(20%)，持续 15 min。
  2. 采集：成功率、错误码分布、P50/P95/P99、队列长度、资源利用率、配额消耗。
  3. 抽样 10 个成功产物执行 QUAL-03/QUAL-02 判定与 DATA-01 三档观测。
- **预期结果**：成功率 ≥ 95%；P95 ≤ 30 s（若因共享模型配额导致的排队有明确提示与预期等待时间）；无实例崩溃/OOM；超时请求有明确失败提示而非无限等待；**并发不得以牺牲生成质量与持久化为代价**（抽样 AQ 通过率 ≥ 0.85、持久化三档通过）。
- **实际结果 / 结论**：＿＿

### E2E-04 并发梯度与容量拐点
- **优先级**：P1
- **前置条件**：同 E2E-03；按 E2E-01 基线确定起始并发。
- **操作步骤**：
  1. 依次以 5 / 10 / 20 / 40 / 80 并发各运行 5 min。
  2. 记录每档 P95、成功率、队列深度、配额错误率。
  3. 找出 P95 首次超过 30 s 或成功率首次低于 95% 的档位，记为拐点。
- **预期结果**：5/10/20 档满足 SLO；拐点被明确记录（作为容量上限依据）；拐点后系统行为可预期（排队 + 明确等待提示，或限流拒绝），**不得静默失败、不得返回半成品应用且不声明**。
- **实际结果 / 结论**：＿＿

### E2E-05 Agent 依赖故障下的端到端降级
- **优先级**：P0
- **前置条件**：可独立注入模型服务故障、构建服务故障、存储故障。
- **操作步骤**：
  1. 注入模型服务不可用，提交 10 次生成，观察用户侧表现。
  2. 注入构建服务故障，提交 10 次生成。
  3. 注入存储服务故障，对已有应用执行 10 次写操作。
  4. 恢复服务后重复相同操作。
- **预期结果**：给出明确的可读失败提示与建议（重试/稍后），不出现无限 loading 或空白页；不返回半成品应用冒充成功；已存在应用在平台故障期间仍可正常访问（生成链路故障不得影响已上线应用可用性）；恢复后行为与故障前一致；无堆栈/内部地址泄漏。
- **实际结果 / 结论**：＿＿

### E2E-06 稳定性与资源泄漏（长时运行）
- **优先级**：P1
- **前置条件**：混合负载（生成 + 修改 + 回滚 + 访问已有应用），时长 ≥ 2 h。
- **操作步骤**：
  1. 连续运行 2 h，每 10 min 记录平台内存、句柄、连接池、队列深度、活跃应用数。
  2. 对比首尾 30 min 的生成 P95 与成功率。
  3. 检查是否存在生成产物堆积未清理（孤儿预览环境、孤儿版本存储）。
- **预期结果**：内存无单调增长；首尾 P95 差值 ≤ 20%；成功率不随时间下降；无连接池耗尽；孤儿资源有回收机制（预览环境数量不无限增长）。
- **实际结果 / 结论**：＿＿

### E2E-07 幂等性与重复提交
- **优先级**：P2
- **前置条件**：可构造同一 request_id 重放与相同需求重复提交。
- **操作步骤**：
  1. 同一 request_id 重放 3 次（含并发重放）。
  2. 相同需求连续提交 3 次，检查是否产生 3 个应用/3 个版本。
  3. 检查重复提交的计费/配额计数行为。
- **预期结果**：重放不产生重复应用、重复版本或重复计费；重复提交行为符合平台声明（允许创建新应用，但须去重提示或明确区分）；无因重放导致的版本历史污染。
- **实际结果 / 结论**：＿＿

### E2E-08 完整用户旅程（生成 → 使用 → 修改 → 回滚 → 再修改）
- **优先级**：P0
- **前置条件**：环境健康；一条典型需求与 2 轮修改脚本就绪；数据观测可用。
- **操作步骤**：
  1. 提交需求生成 V1，记录耗时；执行 AQ 与 DATA-01。
  2. 使用 V1 录入 ≥ 5 条真实数据。
  3. 提交修改生成 V2，执行新需求 AQ + V1 AQ 回归 + DATA 三档观测。
  4. 回滚到 V1，按 VER-03 判定数据策略，执行 V1 AQ。
  5. 基于 V1 提交新的修改生成新版本，执行 AQ + DATA 三档观测 + 回滚到 V2 验证历史可回溯。
- **预期结果**：全旅程无阻断；每步耗时满足 30 s 口径；数据在生成→修改→回滚→再修改全过程中无静默丢失；每步均产出可访问且可交互的应用；全程 trace 可完整追溯；最终结论：生成、交互、持久化、修改、回滚五项能力在同一应用上可组合成立（**这是本平台最重要的验收用例**）。
- **实际结果 / 结论**：＿＿

## 12. 缺陷分级与退出标准

**缺陷分级**：

| 级别 | 判定范围 |
|---|---|
| P0 | 生成应用不可运行/不可交互；数据静默丢失或未持久化；跨用户/跨应用数据泄漏；修改或回滚破坏已有数据；回滚后应用不可用或半新半旧；占位代码冒充实现；能力外需求用假实现冒充；30 s 口径全面不达标 |
| P1 | 需求透传率/回归率/约束保持率未达阈值；AQ 通过率未达阈值；并发一致性缺陷；故障恢复不达标；可观测性缺失导致无法定位 |
| P2 | 体验、文案、响应式、性能边界、幂等提示、审计信息不全 |

**测试退出标准**（全部满足方可发布）：

1. 全部 P0 用例通过，且无未关闭 P0/P1 缺陷。
2. 链路：链路成功率 ≥ 0.95；交接契约合规率 100%；需求透传率 ≥ 0.90 且核心 AR 无丢失；失败可定位率 100%；失败恢复 ≥ 0.90。
3. 生成质量：可运行率 ≥ 0.95；可交互率 100%；AQ 通过率 ≥ 0.90 且 P0 流程 100%；占位代码率 = 0。
4. 持久化：三档观测通过率 ≥ 0.98；数据隔离 100%；并发写丢失率 = 0；修改与回滚后数据延续性 100%。
5. 多轮修改：修改生效率 ≥ 0.95；回归率 ≥ 0.95；历史约束保持率 ≥ 0.95；多轮衰减 ≤ 10 个百分点。
6. 版本回滚：回滚成功率 100%；一致性 ≥ 0.98；完整性 100%；回滚后数据策略与声明一致率 100%；可逆率 ≥ 0.95。
7. 端到端：生成 P95 ≤ 30 s；修改与回滚 P95 ≤ 30 s；20 并发 15 min 成功率 ≥ 95%；故障注入下降级行为符合预期。
8. 所有阈值均有样本量、分子/分母与 Wilson 95% 置信区间记录；语义类指标标注一致性 κ ≥ 0.8；每条用例附 trace_id 与产物留档。

## 13. 需求待澄清项（建议在测试执行前与产品确认）

1. **30 秒口径（最关键）**：是"提交需求 → 应用可访问"、"→ 首屏骨架可见"，还是"→ 完全可交互"？是否同样适用于**修改**与**回滚**操作？本设计取"首次可交互"为总口径并对修改/回滚单列阈值，若产品定义不同须回改 §3.6 与 E2E-01/02。
2. **版本粒度与触发方式**：每个版本由每次修改自动产生，还是用户手动保存快照？版本是否可命名、可删除、可对比 diff？
3. **回滚语义**：回滚后数据如何处理（保留 / 迁移 / 回退到旧快照 / 提供备份导出）？回滚是否产生新版本？是否支持"部分回滚/选择性回滚"（只回退某一轮修改）？
4. **数据持久化边界**：平台是否为生成的应用提供托管存储，还是仅生成代码、由用户自备数据库？应用**删除**后数据保留多久？是否需要数据导出/导入能力？
5. **交互定义**：是否需要支持文件上传、实时通信、登录鉴权等"高级交互"，还是仅表单与列表的 CRUD？
6. **多轮修改的上下文窗口**：可追溯多少轮历史？超出后是摘要压缩还是丢弃早期约束？这直接决定 ITER-02 的期望值。
7. **并发口径**：20（或 N）并发是单实例验收上限还是可水平扩容后的服务级目标？模型配额上限是多少、排队是否可接受？
8. **可用性与 SLA**：需求未给 SLA，建议补充（如月可用性 99.9%、生成任务最长等待时间），否则 E2E-06 与失败恢复类用例缺少判定基准。
9. **能力边界清单**：平台明确不支持哪些需求（支付、短信、外部 API、多租户）？需要一份书面清单，否则 CHN-06 的判定依赖主观。
10. **多用户与权限模型**：生成的应用是否需要登录/多用户数据隔离？平台自身是否需要团队协作与回滚权限控制（影响 DATA-04、VER-07 的期望值）。
